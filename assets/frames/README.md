## ⚠️ 光看 PNG 是判断不出好坏的

**镂空窗口是全透明的，在系统看图器里只会显示成一片棋盘格** —— 你根本看不出照片放进去长什么样。
所以项目里带了一个对照脚本：把 `assets/frames/` 里所有相框按各自的窗口贴到**同一张照片**上，
拼成两张图（竖版一张、横版一张）：

```powershell
# 在项目根目录
python scripts/preview_frames.py                          # 用内置的合成示意图
python scripts/preview_frames.py 你的照片.jpg              # 用自己的照片
python scripts/preview_frames.py 你的照片.jpg 输出.png     # 顺便改输出路径
```

默认输出 `assets/frames/_preview.png`（竖版 7 张）与 `assets/frames/_preview-landscape.png`
（横版 4 张）；下划线开头的文件已被 `.gitignore` 排除。脚本跑完还会**对账**：
把 `preview_frames.py` 里的 `SPECS` 像素窗口和 `src/constants/frames.ts` 的归一化值互相换算，
两边不一致就报出来 —— 11 张必须全部对上。
**改完相框一定要看一眼这两张图。** 脚本里 `FRAMES` 表的 label 一律用 ASCII ——
Pillow 的默认字体没有中文字形，写中文会全变成豆腐块。

## 自己画一张（或从网上下载后改）必须满足的 5 条

1. **格式：PNG，且必须带 alpha 通道。** JPG 不行（没有透明窗口，照片会被整块盖住）。
2. **照片要露出来的那块必须全透明**（alpha = 0），其余部分随便画（纯色、纹理、字都行）。
   > 判断标准很简单：在系统"预览"里透明处会显示成棋盘格。
   > 注意是"**全**透明"：alpha = 254 的像素在合成时仍会以 1/255 的比例把照片压暗，
   > 成片上就是一圈很淡的脏边。存 P 模式 PNG 可以从根上避免这件事（见文末）。
3. **`aspect` 必须等于 PNG 的真实像素宽高比**，否则相框会被拉伸变形。
   例：`1408 × 1712` → `aspect: 1408 / 1712`。
4. **尺寸建议长边 1200 ~ 2400 px。** 太小 → 相框边缘放大后发虚；太大 → 内存吃紧、启动变慢。
   本项目成片分辨率 ≈ 屏幕逻辑尺寸 × PixelRatio（约 1170 × 1600 px 量级），所以 1950 px 长边足够。
5. **镂空窗口不要贴着 PNG 边界**，四周留出实体边框：实体太窄的话，取景器和成片里都会看不到边框。
   （`sheet8x10` 的左右片边只有 24 px，是**故意**的 —— 那是 8×10 散页的真实比例，
   但你换图时要知道这一条。）

## 量出归一化窗口（3 种办法，任选）

**A. Python（最准，推荐）**

```powershell
# 在项目根目录
python -c "from PIL import Image, ImageOps; im=Image.open(r'assets/frames/你的相框.png').convert('RGBA'); print('size=', im.size, '透明区=', ImageOps.invert(im.getchannel('A')).getbbox())"
```

拿到 `size=(w, h)` 和 `透明区=(left, top, right, bottom)` 之后（注意 `getbbox()` 的右/下是**开区间**，
算宽度前不用 +1，写 `frames.ts` 时直接用）：

```
window.x = left / w
window.y = top / h
window.width  = (right - left) / w
window.height = (bottom - top) / h
```

> ⚠️ 别用 `im.getchannel('A').getbbox()`：它量的是"**非**全透明像素"的范围，而相框的纸面一直画到
> 画布边缘，所以它永远等于整块画布 —— 拿它当窗口会得出"窗口 = 整张图"。要用**反相 alpha**，
> 量透明的那个洞。
>
> ⚠️ 反相 alpha 的包围盒也只是"够用"，不是"准确"：**只要这款相框在窗口之外还有别的透明像素，
> 包围盒就会比窗口大**。本仓库里有四张是这样：`neg-135`（齿孔）、`fp100c`（撕边毛边，
> 包围盒顶到整幅画布）、`half-frame`（上缘防挂切口）、`sheet8x10`（切口 + 左下 Notch）。
> 这四张的窗口**只能抄生成脚本打印的值**。
>
> 要自己量这类相框，用**洪泛**而不是包围盒：从窗口中心往外长，长出来的那个矩形才是窗口。
> 多槽的款（`half-frame`）要**逐槽**洪泛再取并集 —— 从并集中心洪泛会正好落在中间那根立筋上，
> 得到 0 px。

**B. Photoshop / 预览 / 任意图片编辑器**：用矩形选区框住透明区域，读选区坐标，再除以画布尺寸。

**C. 直接用对照脚本反查**：改完 `window` 后跑 `python scripts/preview_frames.py`，
看照片有没有正好落在窗口里，反复微调。比 B 快，比 A 慢。

> 其实最省事的是让 `scripts/generate_frames.py` 自己报：它每次生成都会打印每张图的归一化窗口
> （照着抄进 `frames.ts` 就行），画完还会跑一遍**逐像素**的透明区审计 ——
> 期望的透明掩膜是拿窗口常量独立重建的，不是拿画出来的图自己比自己。

改完存盘 → 热重载 → 取景器和成片**同时**变成新相框（两者都由这一份数据算出来）。

### `watermark` 怎么选

右下角那行日期／地点是**后烧上去的一层**，它会盖在相框上。所以：

- **`anchor: 'frame'`** —— 烧在相框的下留白里，像真相机。前提是下留白够宽（**≥ 约 110 px**）
  且那里没有别的印字；用了它，相框的下留白就必须**真的空着**。
- **`anchor: 'window'`** —— 烧在**画面内部**右下角，永远不会和边框上的字打架。
  下留白很窄、或者那里已经排了东西的相框必须选它。
- **`tone: 'graphite'`** —— 细的灰色打字机字，给"下巴本来就是纯白留白"的相框（拍立得、幻灯卡）。
  **`tone: 'amber'`** —— App 里那颗橙色点阵液晶。别把橙液晶烧在象牙白卡纸上，两种材质对不上。
- **`align`** —— 靠左还是靠右。`uppercase` 只对 `graphite` 有意义（打字机字全是大的）。

七张竖版的选择都是有原因的：

| 相框 | 选择 | 为什么 |
| --- | --- | --- |
| `polaroid-600` | `frame` / `graphite` / 左 / 大写 | 下巴 376 px 全空，是留给人写字的；一次成像的记号习惯打在下巴左侧 |
| `instax-mini` | `frame` / `amber` / 右 | 下巴 406 px 全空；迷你画幅就是这台 App 的"默认机型"，沿用原来的橙液晶 |
| `neg-135` | `window` / `amber` / 右 | 下留白只有 281 px，而且片边已经印了 `PROCESS C-41` —— 再烧字就压到工艺号上了 |
| `slide-mount` | `frame` / `graphite` / 右 | 下方 285 px 是空卡纸；卡纸上的字是浅灰印刷体，水印也得是灰打字机字才不打架 |
| `fp100c` | `frame` / `amber` / 右 | 下巴 **696 px** 全空（撕拉片的下巴本来就最宽）；纸是暖白的，橙液晶压得住 |
| `half-frame` | `frame` / `graphite` / 左 | 下巴 240 px；这一款的下巴**偏窄**，靠左放避开右下角的橙液晶（同机橙点会和 `polaroid-600` 那种大留白打架） |
| `sheet8x10` | `frame` / `amber` / 右 | 下巴 638 px **纯黑片基**：浅灰打字机字压不住黑底（对比度不够），橙液晶在黑底上最清楚 |

## 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 照片被整块挡住 / 只看到相框 | 窗口不是透明的（PNG 没 alpha 或用了 JPG） | 重新导出带透明通道的 PNG |
| 相框明显被拉扁/拉长 | `aspect` 与真实像素比不一致 | 按真实像素改 `aspect` |
| 横拍照片被硬塞进竖版边框、齿孔压扁了 | 这一款没有 `landscape`，走了竖版窗口 | 给这款补一张横版 PNG 与 `landscape` 字段 |
| 成片里照片位置偏移 | `window` 量错（尤其拿 `getbbox()` 量了非透明区） | 用上面 A 方案；有边缘特征的款要用**洪泛** |
| 成片里窗口边缘有一圈很淡的脏边 | 窗口/孔周边的 alpha 不是 0 而是 254 一类的值（量化时被平均掉了） | 存 P 模式 PNG，并让审计断言"半透明像素 = 0 px" |
| 取景器和成片构图差一点 | 取景器显示的是相机传感器中心裁切，成片是整张照片中心裁切 | 见 README「已知限制」第 2 条 |
| 日期看不见 / 日期压在印刷字上 | `watermark` 选错（`frame` 撞上了片边的工艺号），或横版的 `frame` 落在**右侧**留白上 | 调 `watermark.anchor`，或改预设的 `watermark.tone`；横版要单独核一遍 |
| **相框上有半透明的字被照片压住了** | 字画到了窗口**里面**（相框 PNG 是盖在照片之上的图层，窗口那块是透明的，字就落到照片上了） | 字必须画在**窗口之外**。生成脚本里的窗口审计会逐像素比对，加完相框记得跑一次 |

## 重新生成

```powershell
python scripts/generate_frames.py                       # 全部 11 张（7 竖 + 4 横）
python scripts/generate_frames.py neg-135               # 只重画其中一张（名字 = 文件名去掉 .png）
python scripts/generate_frames.py neg-135-landscape     # 只重画它的横版
```

需要 Pillow（`pip install Pillow`）。脚本是幂等的，会覆盖同名文件，打印每张图的归一化窗口，
然后跑透明区审计：**任何一张对不上（尺寸、逐像素掩膜、半透明像素）都会 `exit 1`**，
所以"生成成功"这四个字是有依据的。

> **相框不要用 `scripts/generate_placeholder_assets.py` 生成。** 那个脚本早期版本里也画相框，
> 现在只负责 `assets/textures/` 下那几张贴图 —— 相框那部分已经从它里面删掉了，
> 就是为了避免"跑一次贴图脚本，新相框被悄悄覆盖回旧设计"。

### 纸张的棉浆纤维噪点（`fiber`）

要求：**所有相纸类相框**（`polaroid` / `instax` / `slide` / `fp100c` / `half-frame` / `sheet8x10`）
的卡纸底色上烘进一层**低频纤维噪点**，峰值幅度 **3 ~ 4%**。
（`sheet8x10` 的片基也算"纸面"处理 —— 它是有纹理的片基；`neg-135` **不加**：那是黑片基，
3% 的纤维压在全黑上只会变成噪点。）

**为什么是"烘进 PNG"而不是运行时叠一层**：运行时叠就是**每帧多一次全屏合成**，
而这个噪点在整个 App 生命周期里一个字都不会变。烘进去是零成本。

四条量化判据（`scripts/_probe_fiber.py` 会逐款打印，`neg-135` 走"不加"分支当对照组）：

1. 峰值 α ∈ 3% ~ 4%（实测**全部 3.53%** = `9/255`）；
2. 烘完的标准差 **σC > σA**（噪点真的进了图）；
3. 中位数 |ΔB − ΔA| ≤ max(0.5, 峰值 α)（纸色没被整体搬走）；
4. 底色均值 |μC − μA| ≤ max(0.5, 0.35 × 峰值 α)（直流补偿配平得住）。

实测（`μA → μC` / `σA → σC`）：`polaroid` 245.361 → 245.240 / 1.865 → 3.982；`instax`
249.668 → 249.555 / 1.359 → 3.766；`slide` 227.961 → 228.268 / 1.643 → 3.720；
`fp100c` 244.538 → 244.463 / 1.871 → 3.956；`half-frame` 233.607 → 233.777 / 1.471 → 3.680；
`sheet8x10` 9.465 → 12.114 / 1.289 → 4.010（`sheet8x10` 的均值被抬高 2.6 是**物理必然**：
片基 RGB 只有 10，±9α 的纤维只能把亮度**抬**起来 —— 暗股夹在 10 上几乎不产生变化，
亮股实打实提亮一档）；`neg-135` 对照组 Δ = 0.000（σA 2.296）。

**噪点不影响透明通道**：纤维只作用在"不透明"的纸面像素上，写盘前 alpha 仍然被二值化，
审计里"半透明像素 = 0 px"这一条对**每一张**都成立。

### 为什么相框存成 P 模式（255 色 + 1 个透明索引）而不是 24 位真彩

`generate_frames.py` 的 `save()` 在写盘前做三件事：把 alpha **二值化**（>0 即 255）、
把 RGB 量化成 255 色（`method=Image.MEDIANCUT, dither=Image.Dither.NONE`）、
再把调色板第 255 号留给"透明"（`info['transparency'] = 255`）。

**一、也是最重要的一条：只有把 alpha 二值化，透明窗口才是真的透明。**
`quantize()` 是按簇给调色板取平均色的 —— 镂空窗口里的像素 RGB 还是纸的颜色（只是 alpha = 0），
它和纸面相邻像素的颜色几乎一样，于是被并进同一个调色板槽，**纸面的 alpha 被"平均"下来**。
实测踩过的坑：`instax-mini` 有 729705 个纸面像素的 alpha 被平均成 **254**，
`slide-mount` 的孔边一圈 4922 个像素被平均成 **150** —— 这两种都会让照片以 1/255 的比例透上来，
成片上是一圈极淡的脏边，肉眼说不清哪里不对但就是"脏"。

P 模式 PNG 只有**一个**透明索引，天然是二值的，平均动不了它；所以
`save()` 先把 alpha 二值化、再走 P 模式落盘，审计里"半透明像素 = 0 px"这一条就是钉这件事的。

**二、省体积 —— 但只省一点，别指望它。**

| 相框 | 24 位 RGBA | P 模式 255 色 | 倍数 |
| --- | --- | --- | --- |
| `polaroid-600` | 140.6 KB | 116.7 KB | 1.2× |
| `instax-mini` | 104.4 KB | 83.4 KB | 1.3× |
| `neg-135` | 70.0 KB | 49.5 KB | 1.4× |
| `slide-mount` | 381.2 KB | 242.9 KB | 1.6× |
| `fp100c` | 208.7 KB | 162.8 KB | 1.3× |
| `half-frame` | 197.3 KB | 172.9 KB | 1.1× |
| `sheet8x10` | 99.0 KB | 78.8 KB | 1.3× |
| 四张横版 | 728.5 KB | 502.1 KB | 1.5× |
| **合计（11 张）** | **1929.8 KB** | **1409.1 KB** | **1.4×** |

> **这个 1.4× 是"纤维真的在 PNG 里"之后的数字。** 更早的版本曾经是 12.0×（506.0 KB → 42.3 KB），
> 那个数字**看起来漂亮但是假的**：当时的量化器是 `Image.FASTOCTREE`，它不是自适应聚类，
> 而是**每通道固定均分成 16 格**（格宽 16 级）的八叉树。一维阶梯实测：斜坡 `0…255` 只保留
> **16 档**；斜坡 `240…255` 只保留 **1 档**。而 `instax-mini` 的纸色正好落在 **240…255 这一格之内**
> → 整张纸被并成 1 个色号，**纤维在成品里彻底不存在**（量化前同一块纸 unique=35、luma 240~254、
> σ=3.713；量化后 unique=1、luma 恒 248、σ=0.000）。
> 换成 `MEDIANCUT` 之后纤维保住了（35 个色号、σ=3.766），代价就是体积。
>
> 试过并**否掉**的省体积办法：调色板按亮度重排索引（反而略涨）、降到 4bpp、
> 开 `FLOYDSTEINBERG` 抖动（对 PNG 调色板索引无效）、`FIBER_LEVELS` 从 9 降到 5/3
> （省不到 5%，而且会让"9 级"的语义失效）。降色数（255 → 192/128/96/64/48）也几乎不省。
> **唯一的真旋钮是丝宽**：一块 400×400 纸面在 `thread_px` = 4 / 8 / 12 下是
> 108.8 / 85.7 / 77.7 KB —— 仍然取 4 px，因为纸浆纤维本就该是"看得到但数不清"的尺度，
> 为了体积把它放大成 12 px 方格才是真的假。
>
> 也别拿这个体积当质量指标：调色板量化是聚类的，同样的画布换个纸色，索引字节的熵就会变。
